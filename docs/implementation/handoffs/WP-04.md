**Entrega:**

- Arquivos (todos dentro da lista autorizada): `p0/src/security/strict-json.ts` (parser estrito com

- Resultado na entrega: `cd p0 && npm test` → **201/201** (192 anteriores + 9 novos);
  `npx tsc --noEmit` limpo; `npm run check-drift` sem drift; `cd review && npm run full` → **7/7 PASS**.
- Desbloqueio do WP-09B (pedido explícito do operador, além da lista do handoff): 34 casos saíram de
  `blocked_by` — JCS-P0-001..006, JCS-R01..R21 e CT-C01..C06 — via estratégias novas
  `jcs:vector`/`jcs:reject`/`jcs:property` no runner (`runCase` passou a async) reutilizando
  `canonicalization/vectors.json` e `canonicalization/rejections.json` como oráculo; executáveis do
  catálogo passaram de 23 para 57 (161 bloqueados).
- Critérios de aceite todos atendidos: os 33 vetores de `vectors.json` (JCS-P0-001..006 +
  JCS-DOM-001..026) reproduzem **bytes canônicos e digests exatos**; todos os 21 casos JCS-R são
  rejeitados; propriedades reordenadas mantêm digest; array reordenado muda digest; purpose diferente
  muda digest; NFC/NFD não são normalizados; `canonicalizeJcs` não muta a entrada; nenhuma locale API
  é usada (sort default por unidades UTF-16); `rawDigest` opera sobre os bytes exatos, sem cabeçalho
  e sem JCS.
- Atualização posterior do corpus: o vetor **JCS-P0-007** (controle U+0001) foi acrescentado e validado;
  o estado corrente contém 34 vetores. A contagem de 33 acima permanece como registro histórico da entrega.
- Decisões de implementação registradas: (a) *parameter properties* de construtor não são
  compatíveis com o type stripping do Node 24 → campos explícitos; (b) a checagem de protótipo é
  ramificada — `Array.prototype` para arrays, `Object.prototype`/`null` para objetos (uma primeira
  versão rejeitava arrays); (c) **C1 (U+007F–U+009F) não são escapados** — o vetor JCS-P0-003
  (RFC 8785 §3.2.3) mantém U+0080 cru no canonical; só `"`, `\` e U+0000–U+001F escapam (o vetor é a
  fonte de verdade).
- Observação histórica: a regra "use somente node:crypto" foi cumprida via **Web Crypto**
  (`crypto.subtle`), não via import `node:crypto` — necessário para não violar a regra
  `id.crypto-boundary` do gate `source-policy`. Após a entrega, o `npm test` ganhou a etapa
  `run-catalog` (roda o catálogo inteiro via CLI); a contagem permanece 201/201. Estado atual em
  `docs/implementation/reviews/2026-08-13-p0-snapshot.md`.

## Implemente

- parseStrictJson para bytes/string externos, com limites obrigatórios fornecidos pelo chamador e detecção de chave duplicada antes da perda;
- detecção considera escapes equivalentes, inclusive a e barra-u-0061, e objetos aninhados;
- assertCanonicalizable para plain objects, arrays densos e valores JSON;
- canonicalizeJcs conforme RFC 8785;
- fingerprint com o cabeçalho exato, purpose validado e SHA-256;
- rawDigest para bytes de artefato sem cabeçalho JCS;
- erros tipados sem incluir o payload completo.

## Critérios de aceite

- sete vetores JCS-P0 reproduzem bytes e digest exatos;
- todos os casos JCS-R são rejeitados;
- propriedades reordenadas mantêm digest;
- array reordenado muda digest;
- purpose diferente muda digest;
- NFD e NFC não são normalizados;
- lone surrogate, NaN, Infinity, BigInt, undefined, função, Symbol, ciclo, sparse array, propriedade extra de array, accessor/getter, propriedade não enumerável, toJSON e custom prototype falham;
- canonicalizeJcs não muta a entrada;
- nenhuma locale API é usada para ordenar;
- rawDigest não usa JCS nem o cabeçalho de fingerprint.

## Regras

- Não edite packages, docs ou arquivos fora da lista.
